Support — Portal Accessibility Checker for JSM

How to ask for help, how to report a security issue, and what this app can and cannot check. This page describes version 2.8.0 — the version deployed in production on 10 November 2026 — and the guidance in it is unchanged since 2.6.0.

Where to ask

Support is handled in the public repository's issue tracker: https://github.com/tgg49099-dotcom/codegeist-jsm-accessibility-checker/issues

This is a one-person project. There is no 24/7 support, no guaranteed response time and no support contract. A report that contains a reproducible example is usually answered faster than a question without one.

  • Open a new issue and describe the problem in one sentence in the title.
  • Say which version you run (Administration → Apps → Portal Accessibility Checker for JSM shows it) and which environment: production, staging or development.
  • Paste the line that starts with Mode: from the result panel — it tells whether the scan ran in jsm or in jira-fallback mode, and how many sources were read.
  • If a finding is wrong, quote the criterion, the message and the location, and say what you expected instead. The rule engine is open source, so the rule can be checked and corrected in the open.
  • Do not paste customer data, ticket contents or personal data into a public issue. Describe them instead.

For a question that does not need the tracker — "is my portal covered?", "can I use it on Jira Data Center?" — the answer is usually already in the privacy notice and in the repository's README.md.

What the app can and cannot check

The app reads your site through the REST API. The REST API returns metadata, not a rendered page. Three things are therefore reported as not checkable, and the app says so instead of guessing:

  • rendered contrast (criterion 1.4.3) — a ratio computed on a white-background assumption is reported as uncertain contrast, never as non-conformant;
  • reading order and focus order on screen (criterion 2.4.7);
  • visible rendered labels (for example the string a portal actually paints on the screen) and target size (criterion 2.5.8).

Six criteria are partial: they produce a signal to verify, not a proof, and each finding says which of the two it is. The complete list, criterion by criterion, is in the repository: docs/CRITERES-WCAG-2.2-AA.md.

The app never says "compliant" or "non-compliant". It produces findings that a human verifies. If you need a certified accessibility audit, this app is not one.

Security issues

Report a suspected vulnerability in the same issue tracker, with the title prefixed [SECURITY]. Please do not open a public issue for a vulnerability that is still unfixed and exploitable — describe it in a private message first and the details will follow.

Known facts about the security model, stated plainly:

  • there is no public URL: the scan is started from a button in the Jira administration page, which Jira renders only for a signed-in administrator, and the resolver refuses any call that carries no signed-in account;
  • until version 2.4.0 the app answered a web trigger declared with authentication: none; that module has been removed in 2.5.0 and its URLs now answer 424;
  • the manifest declares only the read scopes read:jira-work and read:servicedesk-request: no write scope, no admin scope, no egress;
  • the whole source is public, so the behaviour described here can be read directly rather than taken on trust.

Privacy questions

Everything about the data is in the privacy notice: what is read, what is stored (nothing), where it goes (nowhere outside your own tenant), and how long it is kept (not at all). A request to stop processing is a request to remove the app: Administration → Manage apps.
