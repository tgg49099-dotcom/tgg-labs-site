Privacy — Portal Accessibility Checker for JSM

A read-only Atlassian Forge app for Jira Service Management customer portals. This notice says exactly what it reads, what it keeps, and where the data goes.

What the app is

  • An Atlassian Forge app for Jira and Jira Service Management (JSM), app id 33f1227e-0df1-4008-b181-ea9c50b116f5.
  • Read-only: it checks the metadata of a customer portal against WCAG 2.2 AA criteria and reports what it found. It does not change, create or delete anything on your site.
  • Open source under the MIT licence: the source of every line is public, so the behaviour described below can be read directly, not taken on trust: https://github.com/tgg49099-dotcom/codegeist-jsm-accessibility-checker

What it reads

Who may run a scan is decided on the server, not in the page: before reading anything, the resolver and the two MCP tools ask Jira for the caller's own global permissions (GET /rest/api/3/mypermissions?permissions=ADMINISTER,SYSTEM_ADMIN), with the caller's identity and no extra scope. If the platform refuses that question, or answers without those permissions, the scan does not run: you get a refusal, never a report. This is the same check for every caller, whoever calls the function.

Every call is a relative /rest/... path on the site where the app is installed, made with your own Atlassian identity — the identity of the signed-in administrator who started the scan (asUser), never a wider one: the app makes no asApp() call at all. The manifest declares only the read scopes read:jira-work and read:servicedesk-request: no write scope, no admin scope.

If the platform refuses that identity (HTTP 401 or 403, when your account has not authorised the app to read the site on your behalf), the app refuses and tells you what to do. It never returns an empty report: « nothing was read » and « nothing was found » are two different answers, and the app never confuses them.

  • Field definitions (GET /rest/api/3/field) — the labels and descriptions of the fields shown to customers.
  • The list of projects and service projects (GET /rest/api/3/project) — the portals available on the site.
  • The fields of each customer request type (GET /rest/api/3/issue/createmeta/… and GET /rest/servicedeskapi/servicedesk/…/requesttype/…/field).
  • Issue search (POST /rest/api/3/search/jql, 20 results, fields summary and description) — the title and the description of the request types that were scanned.

If the Jira Service Management API of your site reports that the product is not licensed for use, the app falls back to reading the equivalent Jira tickets that carry the same portal strings. It does not read anything else.

What it stores

Nothing. The manifest declares no Forge storage and the code makes no storage call. A scan is computed on the fly and the findings are returned in the response of the scan itself — shown in the administration page to the administrator who started the scan, and downloadable as CSV. The generatedAt timestamp of a scan is part of that response; it is not kept anywhere.

Personal data

The app does not create an account, does not ask for a name or an e-mail address, and has no user profile. Two honest remarks about the content it reads:

  • The title and the description of an issue can contain personal data typed by the people who wrote it — for example a name or an e-mail address in a ticket title. When the app reads the 20 most recent issues of the scanned projects, it therefore reads that content, and an excerpt of it can appear in the scan result.
  • There is no public URL. The scan is started from a button in the Jira administration page (Administration → Apps → Portal Accessibility Checker for JSM), which Jira renders in the administration area, and the app itself decides who may run a scan: the server asks Jira which global permissions the signed-in account holds, and refuses the scan to anyone who does not hold « Administer Jira » (or « Jira System Administrators »). The app also refuses any scan request that carries no signed-in account. Until version 2.4.0 the app answered a public web trigger declared with authentication: none; that module has been removed. The manifest deployed today declares four kinds of module — the interface, three function handlers, two action modules and one Rovo MCP module — and no public module at all.
  • The page offers two optional fields — a name and an e-mail address — so that a reader can see the privacy behaviour: a value typed there comes back masked (C***, c***@***), never in clear text, and it is masked everywhere in the answer where it can be.

What the app never does: it never sends that content to the app developer, to a third party or to any service outside your own Atlassian tenant.

The two Rovo MCP tools

Since production version 2.6.0 (deployed on 9 November 2026), the app declares one more kind of module: a rovo:mcp module, which exposes two read-only tools through Atlassian's MCP server.

  • scan_accessibility(url) runs the same WCAG 2.2 AA scan as the button in the administration page and returns the findings. The URL is never fetched: it is compared with the host of the site where the app is installed, and a URL pointing at another site is refused.
  • list_last_findings() returns the findings that are current at the time of the call, as a compact list. The app stores nothing, so it keeps no history.

Whose permissions they use. The caller's own: the site is read as the person who called the tool, never with a wider identity; if the platform refuses that identity, the tool returns a refusal and reads nothing. What they read: the same relative /rest/... paths as above, through the same two read scopes — no scope was added and none was removed. What they write: nothing. Who can call them: a signed-in Atlassian user who has granted the app access, through Atlassian's MCP server — and, since production version 2.8.0, only an account that holds the global Jira permission « Administer Jira » (ADMINISTER) or « Jira System Administrators » (SYSTEM_ADMIN).

The administrator check is the same one as the button's, and it is made on the server. Before reading anything, the tool asks Jira for the caller's own global permissions (GET /rest/api/3/mypermissions?permissions=ADMINISTER,SYSTEM_ADMIN), with the caller's identity and no extra scope. If the platform refuses that question, or answers without those permissions, the tool reads nothing and returns a refusal — never a report. The check is written once and used by every entry point of the app (the administration page and the two tools); the published source code shows it, and the test suite that guards it is public too.

What they need your site to have. Atlassian's MCP server is part of Rovo, which Atlassian reserves to paid Cloud plans — Standard, Premium or Enterprise (Atlassian's licensing page). A site on the Free plan has no Rovo, hence no MCP server, hence neither of these two tools. The administration page and its scan button work on every plan, including Free. The app itself is free; the Rovo subscription is yours.

Where the data goes

Nowhere else. Everything runs on Atlassian infrastructure — the Forge runtime and the site's own REST API — inside your tenant. The app has no external service, no third-party SDK, no analytics, no telemetry and no cookies. These points were checked against the published source code, not merely intended: the code contains no outbound call to any host, no storage call, and no analytics or telemetry code.

How long data is kept

Not at all. Nothing is written, so nothing has to be deleted. Removing the app from your site (Administration → Manage apps) removes its installation entirely.

Your choices

  • You decide which portal and which request types are scanned. Nothing is scanned unless you ask for it.
  • There is no data to export and no data to delete: the app keeps none.
  • You can remove the app at any time from Administration → Manage apps.
